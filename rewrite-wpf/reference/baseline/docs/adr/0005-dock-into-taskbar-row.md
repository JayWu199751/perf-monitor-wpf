# 小窗可以拖进任务栏那一行：覆盖式，不是嵌入

> 状态：Accepted。几何在 `electron/src/main/dock.ts`（含行矩形派生 `taskbarRow` 与行内判定 `cardInTaskbarRow`），档位常量在 `electron/src/main/widgetWindow.ts`，守卫的节奏在 `electron/src/main/zOrderGuard.ts`。
>
> 2026-10-02 架构收敛：落位、恢复/拖动门控、移动结算与 500ms 防抖保存统一归 `widgetWindow.ts`；原 `widgetDock.ts` 删除，`widgetWindowPorts.ts` 仅映射真实矩形、显示器与摆窗能力。下文 `widgetDock.placeWidget` 等名称是修正发生时的实现位置，现对应 controller 内部的落位路径。位置经 `settingsHub.stagePosition` 形成不可变快照，防抖到期保存当前真值；期间用户改设置也会一起保存最新位置，不再原地改写共享设置。同步 `moved` 重入被门控，退出/销毁提前 flush。`tests/widgetWindow.test.ts` 经真实 adapter 映射覆盖这些时序，三条真机几何约束与 z-order 节奏不变。
>
> 2026-09 补充：守卫这一段从 `widgetWindow.ts` 内联的定时器里拆成独立 module，三件外部能力（行内判定、任务栏句柄、遮挡判定）经 `widgetWindowPorts.ts` 注入。理由不是好看——30ms 间隔、行内状态每 10 拍慢刷、"不在行内连遮挡判定都不问"这三条都是实测出来的钱，原先被 electron import 挡着一条都测不了；现在 `tests/zOrderGuard.test.ts` 与 `tests/widgetWindow.test.ts` 钉住它们，包括「行内状态最多滞后一拍慢刷新」。
>
> 原始测量数据与探针代码在 `prototype/taskbar-overlay` 分支（commit `b7bc69d`）的 `HANDOFF.md`。

Windows 11 **没有**任何"把第三方窗口放进任务栏那一行"的官方 API。本机（25H2 / Build 26200，175% DPI，任务栏在顶，行高 56 物理px = 32 DIP）逐条实测：

- `SHAppBarMessage` 注册 appbar 时，提议 `(2160,0)-(2560,56)`（与任务栏同行）被系统改判为 `(2160,56)-(2560,56)`，**高度压成 0**：OS 拒绝 appbar 与任务栏同行。
- appbar 的代价还是**全宽**的：预留右端 400x56 与预留整条 2560x56，`GetMonitorInfoW` 的 rcWork 同样从 `(0,56)-(2560,1600)` 缩到 `(0,112)-(2560,1600)`。工作区是矩形，占多窄都付整行高度。
- reparent 进 `Shell_TrayWnd` 不可行：Win11 任务栏是 XAML island（子窗口是 `Windows.UI.Composition.DesktopWindowContentBridge`），挂上去不渲染。
- **DWM 把 layered 窗合成在任务栏之下**：原生 `WS_EX_LAYERED` + `UpdateLayeredWindow` 在普通 `HWND_TOPMOST` 下盖不住任务栏（该点像素无变化），而原生**不透明** GDI 窗盖得住（同点变 `rgb(240,240,240)`）。
- Electron 无论 `transparent` 与否都走合成表面，所以拿不到"不透明 + 普通 topmost"这条路：`transparent:false` + `floating` 实测仍盖不住。
- `alwaysOnTop` 七档扫描：`floating` / `torn-off-menu` / `modal-panel` / `main-menu` / `status` 全部盖不住，**`pop-up-menu` 是最低可用档**，再往上的 `screen-saver` 没必要多要。
- `pop-up-menu` 档下逐像素 alpha 完好：透明带与窗外对照点同值（`rgb(76,75,68)` vs `rgb(75,72,65)`）。这只对**真实合成器**成立，`PrintWindow` 仍会拍平 alpha。

## 决策

- **不做"任务栏模式"**：不加设置项、不加窗口工厂、不加 FFI、不加紧凑布局。就是原来那张卡，允许被拖进任务栏那一行。
- 行矩形由 `display.bounds` 与 `display.workArea` 之差算出（Electron 的 workArea 已排除任务栏），**不调 `ABM_GETTASKBARPOS`**。左右侧任务栏时那条带是竖直的，返回 `null`，即不支持内嵌。（实现位置：2026-09 起这条派生连同**行内判定**一起住在纯几何层 `dock.ts` 的 `taskbarRow` / `cardInTaskbarRow`，`widgetDock.ts` 只把真实窗口接到它上面——原先它们在 `widgetDock.ts` 里，被 electron import 挡着，一条测试都没有。）
- 判据是**卡片中心**落在行内（`dock.ts` 的 `cardCenterInRow`，左闭右开）。中心在行外时"贴上边"仍是原来的贴工作区上沿，**已存配置零影响**。
- 进行后**只重算纵向**：垂直居中到该行。横向仍由用户拖到哪算哪——不做托盘对齐、不查 `TrayNotifyWnd`、不引入右边界锚定。
- 档位常量 `WIDGET_Z_LEVEL = 'pop-up-menu'` 放在 `widgetWindow.ts`（该模块刻意不 import electron，常量得留在那儿），创建时设一次、`show` 时重申一次。
- 工厂里的 `alwaysOnTop: true` 只保证"置顶"，**不保证档位**；档位是可见性不变量，归 controller 管（ADR-0001 的分工）。
- 溢出行的部分只有透明边距：窗口 38 DIP 高于行 32 DIP，居中后卡片占物理 y≈6..51，完整在行内。

## 后续修正一：任务栏会把它反超（实测）

上线后实测：停在行内的小窗会被 `Shell_TrayWnd` **重新插到前面**，从此一直压在任务栏半透明材质之下——
用户体感是"整块消失"，实测是窗口存在、位置正确、`WS_EX_TOPMOST=True`，但 z 序在任务栏后一格。

- **触发器**：点任务栏上的应用图标切应用（explorer 在那一刻重新申请自己的 topmost 位置）。**Alt+Tab 不触发**——它不碰任务栏窗口。
- **不会自愈**：一旦被反超就永久保持，直到窗口重新 `show`（`show` 处理器会重申档位）。
- **档位不是解法**：`screen-saver` 与 `pop-up-menu` 都能盖住任务栏，但都在同一个会被反超的带里；换档只是改变概率，不改变性质。
- **修法（已采用）**：z-order 守卫。每 200ms 检查一次"**卡片中心那一像素是否被 `Shell_TrayWnd` 的根窗口占住**"，
  且仅在**小窗停在行内**时成立才重申档位。判据 `needsZReassert` 是 `dock.ts` 的纯函数（四种组合都有单测）；
  FFI 侧只比句柄不读类名，避开 AGENTS.md 记的按地址解字符串 AV 坑；每次现查 `FindWindowW`，explorer 重启换句柄也不会失效。
- **轮询间隔就是闪烁时长**：200ms 轮询时用户看到"点任务栏会闪一下"，闪的就是守卫捞它的那 200ms。压到 30ms（≈两帧）后实测恢复耗时 **13ms / 20ms**，10 次点击中仅 2 次被反超（守卫生效后不再每次都被压）。
- 开销（A/B 实测，主进程 15s CPU 折单核占比）：**30ms 定时器本身几乎免费**（空转定时器 1.04% ≈ 关掉守卫的基线 1.25%），贵的是每拍的工作量。
  未优化时 **2.92%**；把 `FindWindowW` 的任务栏句柄缓存起来（跟着 300ms 慢刷新一轮重取，explorer 重启可自愈）降到 **1.98%**——字符串→UTF-16 编组是主因，
  别信"三个 user32 调用能有多贵"这种外推；再给"不在行内就直接早退"补上短路（JS 会先求值全部实参，所以 `needsZReassert(a, f())` 里的 `f()` 无条件执行），
  降到**行内 1.46% / 悬浮 0.73%**，即悬浮态与基线（0.94%）已在噪声内不可区分，只有真把小窗停在任务栏里才付约 0.5% 单核。
- 悬浮态**不启用**守卫：被别的窗口盖住是正常 z-order，抢它反而会压住用户的录屏 HUD 之类。

## 后续修正二：横向可选「行内居中」

上线后新增可选规则（共享应用菜单 checkbox「任务栏内水平居中」，持久设置 `centerInTaskbarRow`）：
开启后卡片中心在行内的小窗**水平居中到行矩形**。上面「横向仍由用户拖到哪算哪」降级为默认行为。

- 与"不做托盘对齐"**不冲突**：当初否决的是查询任务栏子控件几何来**避让**（`TrayNotifyWnd`、中部图标）；
  居中只依赖已有的行矩形，零新判据。代价是既认代价的延续——居中的小窗正好盖住 Win11 居中的
  开始按钮与任务栏中部图标并吃掉那一小块点击，这一点在实现前与用户明确确认过。
- 行内**横向由规则独占**：拖动跟手，松手结算一律弹回居中（与贴边"松手才结算"同构，
  是 `dockedPosition` 的又一个纯分支，无转移状态）。曾考虑"仅进行内那一次居中、落点后自由"，
  需要记住行内/行外的转移历史，且"拖歪一次就再也回不了中"，否决。
- 规则只依附"进内"落点：中心在行外、无行矩形（左右侧任务栏）、未贴顶/底时一概不生效；
  顶行与底部占位带同一规则，多显示器仍按窗口中心所在屏。居中是几何不动点，重启二次结算不漂移。
- 勾选变化立即作用于当前状态（已在行内则弹回居中，取消则原地不动）；落盘沿"存实际位置"
  的既有约定，不为"上一次自由位置"保留影槽位。菜单是唯一入口，设置窗不露出该开关。

## 后续修正三：行内垂直居中改为「量真高」，不再预测 OS 钳制（2026-09）

用户报「小窗在任务栏的垂直方向上没有居中」。真机量（`scripts/dock/probe-row-center.cjs`，175% DPI、任务栏在顶、fs12 全指标）分三层看这件事：

- **参照是对的**。派生行（`display.bounds − workArea` = 0..56 物理px）与 `Shell_TrayWnd` 的 `GetWindowRect`（0..56）、与逐点归属扫描出来的那条带（0..55）三者一致 ⇒ 「任务栏行」这条几何没错，错的是落点。
- **卡片在窗口内是居中的**。用 capturePage 位图的 alpha 边界量卡片矩形，实测卡片中心离客户区中心 **0.19~0.55 CSS px**（那点残差是 Chromium 给小数高卡片吸附像素网格的固有下限）⇒ 「把窗口居中到行就等于把卡片居中到行」这条算法成立，问题不在它。
- **错在"预测钳制"**。窗口落尺寸之后 OS 真给的高度，与 `windowSizingFor` 原先预测的 `actual = max(请求高, 窗口现高)` 差 1~4 DIP：创建期窗口 **41 DIP**（客户区 40），而按请求高 20.57 落尺寸后实到 **37 DIP**。这半格误差直接变成偏心——实测上下留空 **7.74 / 11.26 物理px**、卡片中心比任务栏中心高 **3.00px**（窗口 y=-7..57）；在 56px 高的任务栏里就是"卡片骑着上沿"。

**改法**：`widgetDock.placeWidget` 把落位拆成「① 落尺寸 → ② `getBounds` 回读 OS 真给的矩形 → ③ 用真矩形求解 → ④ 落位」。同一条路径复测：卡片中心离任务栏中心 **1.00px**（窗口 y=-5..59，上下留空 9/11）。余下 1px 是两条硬下限之和，不再追：

- **y 只能整 DIP**：Electron 的 `setPosition`/`setBounds` 收到小数直接抛 `conversion failure`（实测），所以 ≤0.5 DIP（≈0.9 物理px）的取整误差是这条路的地板。
- **OS 给的高度在 36~38 DIP 之间抖 ±1 DIP**，而且与落点 y 的奇偶相关（同一请求高，y=-2 时实到 38、y=-3 时实到 37）⇒ 求解**不收敛**：迭代一轮会在 `y=-2/实到 38` 与 `y=-3/实到 37` 之间来回（实测两种状态的偏心分别 +0.99 / −1.76 物理px），多跑一轮换不到更准，只会来回跳。所以**一条路只解一次**，不要写 settle 循环。

**顺手修掉的漂移**（同一支量具的 L2 段）：`useContentSize` 的窗口，凡是用 `setPosition` / `setSize(现尺寸)` / `setBounds(现尺寸)` 落位，窗口高**每次 +1 DIP 往上爬**（连调三次 39→40→41），卡片跟着往下漂半格（0.72→1.75→1.75 物理px）——那条路径把"客户区尺寸"当"窗口尺寸"又加了一次外框。而重述**请求尺寸**时三次都是 37 DIP。所以落位一律"尺寸 + 位置一起给、尺寸取请求值"：`resizeWidgetToContent`、`repositionWidget`、`recheckAndSnap` 三条都照此办理（后两条原先重述现尺寸，每次 show/拖动结算都把窗口撑大一格）。

量具用法（在 `electron/` 下）：`node_modules\electron\dist\electron.exe --no-sandbox scripts/dock/probe-row-center.cjs`
正常模式自己建窗，量「四种落点原语」与「预测式 vs 量真高」两种落法；`DSM_ATTACH=1` 附着到正在跑的实例上，打印它在行内的窗口矩形并把任务栏那一条带存成 PNG。**判据是像素，不是 DOM**：隐藏窗的 `innerHeight`/`getBoundingClientRect` 会滞后于真实窗口（实测 winH=38 时 innerH 仍报 40），拿它当"卡片在哪"会把量具自己变成噪声源。

## 后续修正四：启动恢复前不结算默认位置（2026-10）

用户报「退出前停在任务栏行内，重开后横向不变、纵向贴在任务栏外侧」。首帧 `ResizeObserver` 的尺寸 IPC、窗口创建期的原生 `moved` 都可能早于 `ready-to-show`；当时窗口仍在工厂默认位置，却已经按旧贴边掩码重摆并保存，把记忆的行内坐标覆盖成工作区贴边坐标。真机复现：记忆 `y=-2`，最终落在行外 `y=24`。

启动恢复期间，controller 只记录卡片尺寸，阻止默认位置的重摆与保存。`ready-to-show` 用记忆坐标和已上报尺寸经统一落位原语恢复：落请求尺寸与位置 → 回读真矩形 → 求解；随后才开放移动结算与落盘。恢复入口也不再单独调用 `setPosition`，避免重复加外框高度。行内仍是位置派生状态，不增加持久化模式。`tests/widgetWindow.test.ts` 通过真实贴边端口覆盖顶/底任务栏、居中开/关、尺寸先到/后到及创建期 `moved`，防止只测几何不动点而漏掉启动时序。

## Considered Options

- **AppBar 预留**：官方支持、可交互、别的窗口抢不走。但系统拒绝与任务栏同行（只能落在任务栏**下面另起一行**），且无论占多窄都要付整行 32 DIP 工作区。与"紧凑、小任务栏"的目标正好相反。放弃。
- **覆盖式 + `setIgnoreMouseEvents` 点击穿透 + 独立"任务栏停靠"模式**：位置能精确贴到托盘左侧，但穿透后这块读数完全惰性，且要新增设置项、术语、`DockMask` 取值、渲染层紧凑布局、`Settings` 形状变更。功能上是本方案的超集，复杂度是数倍。放弃。
- **换原生（C++/C#）helper 进程**：唯一实测优势是"不透明 + 普通 topmost"能盖住任务栏；代价是第二个常驻进程、IPC、第二套文字渲染（tabular-nums / 发丝分隔线 / 圆角全部重写）、额外打包与崩溃监管。且不透明矩形贴在任务栏模糊材质上会像一块补丁。放弃。
- **托盘 tooltip / 图标读数**：唯一官方且真在行内的路，零风险零成本，但悬停才看得见数字，与"扫一眼"的初衷相反。放弃。
- **本方案（采用）**：改动面 = 一个纯几何分支 + 一个 z-order 常量 + 一个 z-order 守卫；卡片、拖拽、右键菜单、贴边悬靠、位置持久化全部复用。代价是它压在任务栏之上因而**会吃掉那一小块任务栏的点击**，左右侧任务栏不支持，以及任务栏反超后有一次 ≤200ms 的闪动。
