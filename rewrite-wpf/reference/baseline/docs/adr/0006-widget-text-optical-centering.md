# 小窗文字垂直居中：一条两项抬量定律，常数从像素反解

> 状态：Accepted。本文按时间累积，**「后续修正五」一节才是当前实现**：共线的参照线是各 run 的**主体中线**（不是墨迹外框中线），但**上标单位 `°` 不吃这条**、改吃 cap 线；卡片高度由最大字样的主体墨迹派生，「居中」与「最大字样边距」（WIDGET_EDGE_GAP，现为 6px）都不再是常数问题；a/ρ 两张表只负责各角色彼此共线。下面的「决策」「已知极限」描述被修正二取代的各自成盒模型（那两节里的 `translateY`、"ρ 表与卡高绑定" 都已作废），修正二描述被修正三取代的「卡高钉死 + 常数负责居中」那一版。定律与两张表在 `electron/src/renderer/src/styles/optical.css`，执行处只有一行 `.optical`；判据是 `electron/scripts/alignment/measure.cjs`（`npm run measure:alignment`，五条判据：共线 / 居中 / 边距 / 上标 / 裁切，外加一条字体栈轴），形状守卫是 `electron/tests/opticalCenter.test.ts`，角色名单（含谁豁免共线）在 `electron/scripts/alignment/roles.cjs`。术语见 `CONTEXT.md` 的**光学校正**、**墨迹中线**、**主体中线**、**上标单位**与**最大字样边距**。

## 问题

卡片里的文字混了四档字号（标签 0.82em、主读数 1em、次级 0.9em、单位 0.82em×0.9em），肉眼看着"不在一条线上"。旧实现是 11 个散在 4 个文件里的光学校正量（`translateY(-0.048em)`、`vertical-align: 0.058em` 等），每条注释都写着「整 1 设备px @12px」「@175%」——即它们是**单一字号 × 单一 DPI 下的快照**，不是模型。

量具（真 DPI、真字体栈、`capturePage` 抓合成位图后逐行找墨迹上下沿）实测 HEAD：

- 19 个组合（字号 10–18 × 有值/缺失 × 小窗/设置窗）里 **18 个红**，最差 **4.00 设备px**（fs15 缺失态）。
- 扇形随字号**单调张开**，斜率 +0.20 设备px/字号：fs10=1.00 → fs15=4.00。这才是用户看得见的东西，不是绝对误差。
- fs=12 定位到具体谁在漂：`%` 比相邻主数字低 1.0~1.5 设备px，次级读数与 `°` 高 1.0，箭头 ``↓↑`` 低 1.0。

单变量实验（注入样式把 11 个抬量全归零，不动源码）给出纯基线态的扇形：`%` 从 +1.00(fs11) 张到 **+3.50(fs18)**，`MB/s` 因降部斜杠再低 1.0，`°` 是 −3~−5（上标小圈），而 `clock` 与主数字**逐位一致**（同结构的两个 run 测不出差——这既是量具的自检，也说明差异全来自各 run 自己的排版）。两个机制级错误同时被抓到：**`.direction` 的 translateY 叠在父级 `.reading` 的同值抬量之上**（双抬，实测多整整 1 设备px），以及**数字用 transform（参照主字号）、单位用 vertical-align（参照单位自身 0.82em）**——两套参照随字号线性张开。

## 决策

- **一条定律，一处执行**：`translateY(calc(-1 * var(--rho) * 1em))`，只写在 `optical.css` 的 `.optical` 里。抬量与该 run 自己的 `em` 成正比 ⇒ 与字号无关、与 DPI 无关。
- **让盒中心先重合**：每个会渲染文字的 run 都是独立的 flex 项，且都撑满同一个行盒 `--lh-widget`（= WIDGET_CARD_HEIGHT − 上下各 1px 边框）。盒中心是同一条线，各 run 再抬掉自己的 ρ·em，墨迹中线就落到那条线上。
- **ρ 由像素反解，不由排版推算**：`(中线 − 盒中心)/(em·dpr)`，覆盖 10–18 全档与两态后取均值，得 5 个常数（常规文字 0.037、`--` 0.1188、`MB/s` 0.0936、`°` −0.1734、箭头 0.068）。五个"常规文字"角色实测相差 ≤0.007em（0.15 设备px），在半格网格内，故合并成一个常数。
- **设置窗不接这条定律**（见 Considered Options 里的实测反例）。
- **允许残差，卡住趋势**：允差两条并列——单组合上限 2.0 设备px，且散差对字号的回归斜率 ≤0.08。只有第二条能挡住"把常数再调成某一档的整数"这种回归。

修后：19 组合全绿，最差 2.00 设备px（fs10），斜率 **−0.142**（随字号变大而收拢，与 HEAD 反向）。同一把尺子复算 HEAD artifact：`worst=4.00dev 超上限 11/18 斜率 +0.20 ⇒ RED`。

## Considered Options

- **换一批更准的手调常数**：否证。纯基线实验里所需抬量随字号张开到 3.5 设备px，任何常数都不能同时满足 10–18。
- **拿 canvas `measureText` 的 `fontBoundingBox`/`actualBoundingBox` 推 ρ**（一度是我最想写的漂亮公式 `lift=((a−d)−(A−D))/2`）：**被自己的量具否证**，拟合 `k=0.479 R²=0.584 max|resid|=1.93 CSS px`。原因是混排时 canvas 报的是主字体的量度，不是布局真正用的 strut。同一公式改成运行时现算（页内测量再写回）不但没更好，反而更差（最差 3.0 设备px）。放弃。
- **CSS `round()` 把抬量吸附到设备网格**（保留上一版"整网格点"的发现）：**实测无效**——加与不加，19 个组合逐位相同。文本基线的网格吸附是渲染器行为，CSS 无从干预，`translateY` 最终只能以整设备px 生效。故 `--dpx`、`lib/optical.ts` 一并删除，C 方案最终零运行时 JS。
- **"窗口次像素位置导致跳档"这个解释**（上一版注释的说法）：**否证**。把卡片整体横移 0 / ½ / 1 设备px 三档，各 run 的自然中线**完全不变**（逐位相同）。相位不是噪声源。
- **设置窗一起接定律**：接了反而从 0.50 退到 1.50 设备px。它的行内文字本来就在格网上（同一行盒、同字族），多加一个抬量是纯粹的伤害。已回退，`settings/main.ts` 里留了注释说明为什么故意不接。
- **本方案（采用）**：代价是残差不为 0——见下。

## 已知极限与下一步

Chromium 把文本基线各自吸附到设备网格，实测各 run 的自然中线只落在 **0.5 设备px 的格点**上，而 `translateY` 只能整格生效 ⇒ 独立成盒的文字 run 之间，共线的物理极限是 0.5~1.0 设备px，不是 0。fs10/fs11/fs15 读到的 2.0 来自 `°`、CJK 标签、箭头这几处自然位置本就跨档的角色（CJK 标签的经验 ρ 在 fs10/11 与 fs13+ 之间摆 0.076em，正是格点奇偶而非排版趋势）。

要再往下压，只有一条路：**让整条 bar 共用同一条基线**（`.bar` 从 flex 改为一个 inline 流，各段 inline-block 按基线对齐，发丝分隔线改用等高盒的背景渐变）。届时各 run 的中线差只剩墨迹量数之差，盒中心不再各自取整，理论上可稳定在 1.0 设备px 以内。这条路当时没走，因为收益是 1 个设备像素，代价是把已验证的盒模型再翻一遍——且它是上一版在**段内**走过的方向（`Reading.vue` 注释里的"同流"）。**它已经在「后续修正二」走完并兑现了那一格**，走的时候仍然只认 `measure:alignment`，不认任何推算。

```powershell
cd electron
npm run build          # 量具加载的是 out/renderer 的真构建产物
npm run measure:alignment   # 19 组合，约 5 秒；退出码非 0 即红
```

判据是位图里的墨迹上下沿，不读任何 CSS 常量——这是它能证伪公式的原因。重测 a/ρ 两张表（换机器、换字体栈、改字号阶梯即 clamp 上下限或 0.82/0.9 这些比例时；只改卡片高度不必重测，见修正二）：

```powershell
$env:DSM_CSS='.optical{vertical-align:baseline !important}'   # 关掉定律，量自然位置（定律已是 vertical-align，transform:none 不再能关它）
node_modules\electron\dist\electron.exe scripts\alignment\measure.cjs
Copy-Item scripts\alignment\last-report.json scripts\alignment\natural.json
Remove-Item Env:DSM_CSS
node scripts\alignment\fit-rho.cjs scripts\alignment\natural.json    # 反解 a/rho 两张表
node scripts\alignment\diff-readout.cjs scripts\alignment\baseline-head.json scripts\alignment\last-report.json  # 新旧同尺差分（只出读数；判据归 measure.cjs）
```

自修正五起 `fit-rho.cjs` **按角色分参照**：普通角色抬到卡片中心线，上标角色（名单在 `roles.cjs`）抬到 cap 线。那条 cap 线是从「卡片中心线 − 最大字样墨迹高的一半」推出来的，不是直接读自然态 artifact 里数字的墨迹上沿——那时数字还没被抬，读了就把数字自己的抬量漏算进去。重测的输入就是上面那两步现生成的那份 artifact（`scripts/alignment/*.json` 全在 `.gitignore` 里，本地 scratch，不入库）。

`scripts/alignment/` 是调试装置（假 preload 只在本地被 `measure.cjs` 用，`build.files` 只含 `out/**` + `package.json`，进不了包）。
修正五起这里多一个 `roles.cjs`：run key → 角色的那张表，`measure.cjs` 与 `fit-rho.cjs` 各自 require 它（同一份分类写两处一定会漂移，漂移的形态是「谁豁免共线」两边说不清）。

2026-09 清理：这个目录一度攒到 13 个 `.cjs`，其中 7 个（`fan-table` / `phase-test` / `predict` / `probe-settings-height` / `slope-stat` / `spreads` / `tight`）是本文各次否证的现场脚本——结论都在这里了，脚本没人再跑，也没有任何东西引用它们，于是删掉。`verdict.cjs` 换成了 `diff-readout.cjs`：它抄了一份 `TOL=2.0` 与手拍的 `TOL_SLOPE=0.08`，而量具早已改成 2.5 与 3·SE，同一个 artifact 两份脚本给出相反结论——**判据有两处就一定会漂移**，所以差分器现在只复算读数，RED/GREEN 归 `measure.cjs` 一家。量具里的 `DSM_AUTO` 分支（页内按真实字体度量自动求抬量，38 行）一并删除：那次实验的结论见下方修正二，它留下的只是第二条「谁来摆正文字」的路径，而这条路径正是形状守卫要挡住的东西。留在目录里的：`measure.cjs`（量具与判据）、`collect.cjs` + `preload.cjs`（它的依赖与假 preload）、`fit-rho.cjs`（反解两张表）、`diff-readout.cjs`（差分读数）、`gate-check.cjs`（3·SE 判据自身的对照）。

## 后续修正一：卡高 26 → 22，以及"常数与几何绑定"这件事

用户要求降低卡片高度。实测依据：18 号字的全部文字里最高的墨迹只有 **12.57 CSS px**，而内容盒给了 24px——一半以上是空档。改 `WIDGET_CARD_HEIGHT = 22`、`--lh-widget = 20px`（等式由 `tests/opticalCenter.test.ts` 钉住）。

三件事是这一改新暴露的，都值得记下：

1. **ρ 表与卡高绑定，改卡高必须重测。** 行盒从 24px（=42 设备px，偶）变 20px（=35 设备px，奇），盒中心的取整相位换了半格，各 run 的自然中线整体内外挪半格。沿用旧表实测：fs=14 从 1.50 涨到 **2.50 设备px**（超上限）。重测就是「关掉定律量自然位置 → fit-rho」两步，秒级。
2. **给量具加了裁切判据。** 卡片窗口高 == 卡高，所以降高度有真裁切风险，而原来的量具在 1400px 高的视口里渲染卡片，**根本没经过这条路径**。现在采集 `<bar>` 自己的矩形，要求每个 run 的墨迹落在内容盒（内缩 1px 边框）之内，并顺带报最紧余量：22px 卡下余 6.24 设备px，不裁字的绝对下限 14px。判据自测过：把卡高改成 12 立刻从 fs13 起报 CLIP（CJK 标签最先被切），退出码非 0。
3. **趋势阈值改成统计量。** 原来我手拍 slope ≤0.08，而格点抖动本身就能造出这个量级的斜率——降高度后读到 slope=0.083、却没有任何单调趋势（散差序列 0.5/1.5/1.0/1.0/1.5/1.5/1.5/2.0/1.0），说明门限落在了噪声里。现在按实测残差算 SE，判据 slope > 3·SE。同一判据回头看 HEAD：slope **0.200、σ 0.26、3·SE 0.102 ⇒ RED**（它的趋势是单调的，残差小）；修后 slope 0.083、3·SE 0.156 ⇒ ok。交叉验证脚本 `gate-check.cjs`，里面还记了一条口径警告：同一份 HEAD artifact 按「类均值」口径算散差会得到不同的 3·SE 和相反结论，所以趋势判据只能与它自己的口径一起用。

顺带修掉一处测试失真：`tests/dock.test.ts` 里 `margins` 的兜底断言原来拿场景局部的 `CARD.height = 26` 比对，而 `dock.ts` 兜底用的是 `WIDGET_CARD_HEIGHT`——改常量后它必须引常量才不撒谎；其余场景仍显式传 26，因为 dock 的几何全按传入 content 算，与真实卡高无关。

## 后续修正二：整条 bar 共用同一条基线，尾部收一格

用户的要求是「所有字符的垂直中点落在同一条线上」。上面那节把这条路的入口写在了「已知极限与下一步」里，本轮把它走了：`.bar` 从 `inline-flex` 改成单一 inline 格式化上下文（`.bar` block、`.seg/.val/.reading` inline、`.num` inline-block 保留 `min-width: 3ch` 的定宽数字槽、`.sep` 改为 13px 宽的行盒等高盒 + 背景渐变画那 1x10px 的发丝线），定律的执行器从 `translateY` 换成 `vertical-align`，并新增一项与 `--fs` 成正比的 strut 项：

```css
.optical { vertical-align: calc(-1 * (var(--a) * var(--fs) + var(--rho) * 1em)); }
```

判据仍然只有 `measure:alignment`。同一把尺子、widget 18 组合 414 个 run，量「每个 run 的墨迹中线离那条线有多远」：

| 状态 | 均值 | p90 | 最大 |
| --- | --- | --- | --- |
| 修正一（各自成盒 + `translateY(−ρ·em)`） | 0.32 | **1.00** | **1.50** 设备px |
| 本轮（共享基线 + 两项定律） | 0.31 | **0.50** | **1.00** 设备px |

逐档散差：修正一 9/18 个组合读到 1.5~2.0，本轮 18 个组合里 13 个 ≤1.0（最差 fs14/values 2.0，趋势斜率 0.000 与 −0.042，都在 3·SE 之内）。亚像素判据 `midSub` 基本不动（0.39→0.36 均值）——**这一格赚在「25 次独立取整变成 1 次」上，不是赚在排版模型上**，所以只有行盒判据看得见它。上一节预言的「收益是 1 个设备像素」照本兑现，没有更多。

三条新的否证结论，都比修正一那四条更容易踩：

- **`transform` 在同流之后完全无效**。每个 run 都成了非替换 inline 盒，`transform` 不作用于它——把定律照旧写成 `translateY`，19 个组合的读数与自然态**逐位相同**，即整条定律静默失效、量具全绿而屏幕上什么都没发生。这条只能靠「关掉定律重测必须换执行器」来防：注入样式是 `.optical{vertical-align:baseline !important}`。
- **`align-items: baseline` 配 `translateY` 不是等价的省事写法**。实测自然态与同流一致（4.0~6.5 设备px），但一上抬量就散到 8~12.5，比自然态更糟：transform 会连着 flex item 自己的基线一起挪，父层的基线对齐于是被校正量重新搅一遍。想共享基线就得真的共享，不能借 flex 的 baseline 档。
- **单参照的 ρ·em 定律在同流下追不上中心线**。共享基线离卡片中心线的那一截与 `--fs` 成正比（strut 的 half-leading 把 ascent−descent 摊进行盒后剩下的部分），所以必须有一项跟着 `--fs` 走。只写 ρ·1em 时实测跨档极差 0.135em ≈ 2.8 设备px，全表怎么调都留一个扇形。

代价与新的绑定，说清楚：

1. **表从 5 个数变成 12 个**（6 角色 × 2 项）。而且对 em 始终与 `--fs` 成正比的角色，(a, ρ) 的**分配是弱可辨识的**——挪 a 与 ρ（ρ 增减 δ/ratio、a 减 δ）预测不变，`fit-rho.cjs` 会把这类角色标成单档并把 a 记 0。所以这张表不能按字面读，认的是代回 CSS 后量具绿不绿。
2. **绑定换了对象**：a 表吃 `--fs` 的 clamp 阶梯（`.label`/`.unit` 12px、次级读数 14px、0.82/0.9 这些比例），改字号阶梯必须整表重测；而**卡高不再绑定 ρ 表**——同流之后改 `--lh-widget` 只让整条线一起平移，修正一那条「26→22 沿用旧表 fs14 从 1.5 涨到 2.5」的坑随旧盒模型一起作废。
3. 设置窗仍然不接（`settings/main.ts` 的注释保留）；本轮实测它对 `measure:alignment` 的 settings 组合无影响（0.50 设备px，与修正一相同）。

顺手给量具补了一条判据：artifact 现在每轮带 `cardBox`（内容盒上下沿与中心线，设备px）。有了它 `fit-rho.cjs` 才能直接对着**卡片中心线**反解，而不是对着某个 run 的中线——共线与居中于是同一次拟合同时管掉，也免掉了「参照 run 自己也被吸附过」混进表里的那半格噪声。

## 后续修正三：卡高由最大字样的墨迹派生，居中与最大字样边距从此不是常数问题

用户提的两条：① 不同字号下垂直居中经常失效，而且随字体改变，要一个解决方案；② 最大的字样到可视边框的距离会随字号变小，钉死成 4px。

先补量具，因为**旧量具根本没有这两条判据**：它只算各 run 中线的散差（「齐不齐」），从没算过整条 bar 离卡片中心线有多远（「在不在中间」），也从没算过边距，也没有字体栈这条轴。补完之后同一份 HEAD 立刻可读：

- 居中：散差全绿的 19 个组合里，墨迹并集中心离卡片中心线最大 **1.58 CSS px**（fs17 缺失态），主读数中线最大 **1.87 CSS px**。
- 边距：主读数墨迹到可视边框从 fs10 的 6.58/6.85 一路掉到 fs18 的 **5.44/3.42** —— 「随字号减少」被量到了，而当时 `measure:alignment` 是 GREEN。
- 字体栈：把整栈换成 Arial，散差从 2.00 涨到 **5.50 设备px**（3.1 CSS px）。常数是从生产栈（实测解析到 Segoe UI Variable Text）拟合出来的，换栈即失效，这条以前只能猜。

### 决策：居中交给盒子，不交给数字

`.bar` 改成 `height: auto` + `text-box: trim-both cap alphabetic` + 上下 `padding = --edge-gap(当轮 4px，其后 8px、现 6px) + --edge-bleed(0.34px)`。内容盒被裁成「字号等于 --fs 那批 run 的墨迹外框」（cap 顶 → 基线），用的是此刻**真正解析出来的那族字体**的度量。于是三件事同时成立，而且没有任何可调数字：

1. 内容盒中心就是最大字样的墨迹中心（同一次裁切的两端）⇒ 居中是结构性的；
2. 墨迹到可视边框就是 padding ⇒ 这一格距离随字号、DPI、字体栈恒定；
3. 卡高随字号呼吸：目标 4px 时实测 15.4(fs10) → 21.6(fs18)，8px 时 24.8 → 30.4，6px 时 20.8 → 26.4，而旧写法钉死 22px，等于把这三件事全交给一张表。

定律的形式（`vertical-align: calc(-1 * (a·(--fs) + rho·1em))`）与两个系数不变，但职责收窄成**纯粹的角色间共线**。整表重测（关掉定律量自然态 → `fit-rho.cjs`）后系数只动了 ≤0.043 —— 修正二那条「卡高不再绑定 ρ 表」的预言在这一次又兑现了一遍。

| 同一把尺子 | 修正二（卡高钉死 + 常数居中） | 本轮（墨迹派生） |
| --- | --- | --- |
| 居中最大（生产栈，19 组合） | 1.58 CSS px | **0.16** |
| 主读数中线最大 | 1.87 CSS px | **0.44** |
| 最大字样边距 fs10→fs18 | 6.58 → 3.42 | **4.0 ± 0.5 恒定** |
| 散差最大 | 2.00 设备px | 2.00 设备px（不变） |
| 换字体栈后主读数（7 族） | — | **0.15~0.71 CSS px** |

### 三条要说清楚的口径

1. **边距与居中的参照是「主读数」= 字号等于 --fs 那批 run 的墨迹**（主读数与时钟），不是全条 bar 的墨迹并集。并集里含中文标签、`↓↑`、`MB/s` 的降部，这些角色的比例本身就是字体事实（SimSun 的中文比 cap 线高出一大截），拿并集当参照等于把「居中」重新退化成一张按字体拟合的表。实测分得很开：换栈后并集参照漂到 2.13 CSS px，主读数参照仍在 0.71 以内。并集只用来当**裁切**判据（别的角色不许被切）。
2. **边距允差 ±0.6 CSS px 是物理下限，不是松**：基线吸附到设备网格给 ±0.29，数字 0/6/8/9 在 cap 线之上本就各有一点过冲。旧表里 `--edge-bleed = 0.34px` 补的就是这两者之和的一半（目标 4px 时不补则实测均值 3.66；目标 8px 时实测 7.48~8.31；目标 6px 时 5.48~6.31）。
3. **a/ρ 表仍是拟合事实**：换字体栈必须整表重测，量具现在有这条轴，换栈会直接红而不是静默漂。

### 连带的几何与形状约束

- `WIDGET_CARD_HEIGHT` 从「主/渲染同源的几何真值」降级为**首帧与未上报时的兜底初值**。真值是渲染端的 `offsetHeight`，走本来就在的 `resizeWidget(w, h)` 上报；`dock.ts` 的 `margins()` 与任务栏行内判定吃的都是上报值，所以贴边推出、拖进行内、z-order 守卫那条「卡片中心那一像素」判据全部自动跟着新卡高走。
- `tests/opticalCenter.test.ts` 里「`--lh-widget` == 卡高 − 2」这条等式作废，换成三条：`--edge-gap` 与 `WIDGET_EDGE_GAP` 同源；`.bar` 必须 `height: auto` + 裁到墨迹 + 上下对称边距（且不许再用内联样式下发卡高）；渲染层不许出现 `WIDGET_CARD_HEIGHT`，上报高度必须是量出来的。
- `.sep` 那根发丝分隔线原来是 20px 高的行盒等高盒 + 背景渐变——卡高一改成墨迹派生，它就会自己把行盒撑回 20px，等于用装饰件把几何改回去。改成 0 高、正好落在共享基线上的点，线用绝对定位画 `1cap` 长（跟着最大字样一起呼吸），居中在基线上方半个 cap。

### 一条给下次重测的人

`fit-rho.cjs` 吃的必须是「关掉定律」那份 artifact，而 `DSM_CSS` 是**环境变量，不跨 shell 命令保留**。本轮第一次重测就是在另一条命令里设了它、下一条命令才跑量具，于是 `natural.json` 其实是「定律开着」的读数，拟合一张贴合残差的表（几乎全零），装回去 `°` 直接漂到 6.5 设备px。量具抓到了这件事，但它不会告诉你「量的不是你以为的那个状态」——设 env 和跑量具必须写在同一条命令里。

### 追加：目标边距 4px → 8px → 6px，和一条只有像素判据抓得到的 CSS 语法坑

用户随后把这一格改成 8px（再后来 6px）。**机制一行没动**，改的就是 `WIDGET_EDGE_GAP` 一个数（渲染层的 `--edge-gap` 与量具的 `GAP_TARGET` 各自同步它），卡高因此整体长高 2×4px：实测 24.82(fs10) → 30.43(fs18)，边距读数 7.48~8.31（允差 ±0.6 内），而居中与共线两项与 4px 那轮逐位相同（0.16 / 0.44 CSS px，散差 ≤2.00 设备px）。这就是把边距交给盒子换来的东西：**改目标值不需要重测任何一张表**。

改的过程中踩了一条坑，值得单独记：第一版改动里我写了 `--edge-gap: 8px; // 说明`。**CSS 没有 `//` 行注释**，这一整条声明被丢掉，`--edge-gap` 成空值，于是 `.bar` 的 `padding: calc(var(--edge-gap) + var(--edge-bleed)) 9px` 整个失效，卡片掉到 0 内边距。源码正则那几条形状断言全绿（它们只认文本形状），只有像素判据会红：边距直接读成 −0.20/−0.51，负号就是墨迹跑到内容盒外面去了。现在 `tests/opticalCenter.test.ts` 里加了一条「optical.css 不许出现 `//`」的断言（先把合法的 `/* */` 块摘掉再找，否则注释里提到这个写法会自己打自己），把这类语法级错误从像素那一层提前到单测这一层。

## 后续修正四：参照线从「墨迹外框中线」换成「主体中线」

用户报「网速的数字和 `MB/s` 两条视觉中线不重合」，并提议合并成一个元素。先量他给的截图（同一套逐行找墨迹的判据，输入换成他的位图）：`0.1` 与 `MB/s` 的**墨迹上沿在同一行**，主体中线差 1.5 设备px。根因不是元素边界，是判据：`MB/s` 的斜杠只占取值带一两列，却把外框下沿拖下去一整格，于是「按外框居中」恰好把 M B s 顶到数字的 cap 线上。合并反而更糟——实测把单位改成与数字同字号同抬量（= 真·同一个 run）后最差到 4.00 设备px，因为 `°` 是上标小圈，一旦不许单独抬，它就没处归位了。

于是换参照线：**主体中线** = 覆盖率 ≥ 20% 峰值的最长连续行段的中点，斜杠降部、小数点这类细笔画自动出局。两张表按它重解，`MB/s` 的 ρ 从 0.3303 涨到 0.4598（+0.13em ≈ 1.5 设备px），实测该 run 的主体中线从离群 1.5 格变成 0.00 格。

三条被否证的写法，都比「直接上主体」看起来更聪明：

- **纯视觉重心**（Σ cov·y ÷ Σ cov）：对 `MB/s` 对，对 `↓↑` 错得更狠——`↑` 的墨在上半、`↓` 的墨在下半，重心把两个相反方向各拉 2~3 设备px，而它们的外框本来严丝合缝。最差散差 4.85 设备px。
- **主体阈值取 0.6 倍外框高**：正好落在箭头的摆动区间（杆身占 21%~50%），于是箭头在某些档位换法则，散差从 2.0 抖到 2.5。阈值定在 **0.75** 才分得开：`MB/s` 主体 12/14 行（用主体），箭头 ≤7/14 行（退回外框）。
- **设置窗一起换主体判据**：它的标签是中英混排（同一 run 里 Latin 顶比 CJK 低，主体行段会把它自己切开），读数从 0.50 涨到 2.50 设备px。量具因此按窗口分口径：小窗用主体中线，设置窗沿用外框。

顺带把 `%` 从中英文标签那一档拆出来单独认领一对系数（同尺寸档但形状不同：两个小圈加斜杠）：合并时两边残差各 1.12 设备px，拆开后 label 0.98 / pct 0.60。表从 6 对变 7 对，这是「拟合数换像素」的一次真实开销，跨字体重测的面也更大。

**允差从 2.0 设备px 重定基线到 2.5**，说清楚不是放水：同一份渲染在新尺子下读 2.5、旧尺子读 2.0；而**改之前**用这把新尺子是 3.32~4.85。新尺子多看见的那 1.5 格，正是用户报的那一格。趋势判据（斜率 vs 3·SE）与其余三条判据不变，全绿：居中 0.42、主读数 0.44、边距 8±0.52、散差 ≤2.50；跨 5 族字体主读数仍在 0.15~0.43 CSS px。

## 后续修正五：`°` 不吃共线，改吃 cap 线

用户带截图报：「温度的单位应该在数字的右上角，你把它居中了」。量的就是他自己那一格：`°` 的墨迹在 fs12 读到 `[773,777]`，而同一行数字的上沿在 768——小圈坐在数字的**正中间**，外框中线与共享中线严丝合缝（离群 0.5 设备px），也就是说**它绿着判据长得对，屏幕上却是错的**。

根因不在系数，在参照线。定律把每个 run 的**主体中线**抬到卡片中心线上，这条对标签/数字/`%`/`MB/s` 全对，因为它们的中线本来就该齐；`°` 是上标记号，它的语义是「骑在自己那个数字的右上角」，中线齐了恰恰毁掉它。而且这一版还随字号张开：4→8 设备px（fs10→18），因为单位的 em 被 `clamp()` 钉过档，抬量把小圈越抬越低。修正四那句「合并（单位与数字同字号同抬量）反而更糟，最差 4.00 设备px，因为 `°` 一旦不许单独抬就没处归位」其实已经踩在这条线上，当时把它当成「单位必须能单独抬」的证据，没读成「上标记号的参照线不是中心线」。

### 决策

- **换参照线，不换机制。** 上标角色的目标改成「自己的墨迹**上沿**坐在**最大字样**的墨迹上沿（cap 线）上」。定律的形式 `vertical-align(-(a·(--fs) + ρ·1em))` 一个字没动，执行处仍然只有 `.optical` 那一行——变的只是这个角色反解时对着哪条线。
- **名单一处。** 谁算上标写在 `scripts/alignment/roles.cjs`（顺带把原先长在 `fit-rho.cjs` 里的整张角色表搬过去），量具与反解器共用。这是「判据有两处就一定会漂移」那条的老毛病，只是这次漂移的是「谁豁免」。
- **量具加第 5 条判据，同时把 `°` 从第 1 条里出局**（`assert` 与 `segs` 都算）。豁免与新增必须同一次做：只加判据不让它出局，散差会量到「定律对新参照也归了位」这件好事并把它判红。
- **参照取全条 bar 的最大字样，不取本读数自己的数字。** 两个理由：缺失态那一格是 `--`，它的墨迹坐在数学轴上，跟着它走 `°` 会随有没有数据上下跳；且 cap 线正是 `.bar` 的 `text-box` 裁出来的那条线，全条 bar 的上标记号落在同一条线上才是设计。次级读数（0.9em）的 cap 顶比最大字样低 1~2 设备px，这个差值由允差吸收。
- **存在性守卫**：widget 组合里一个上标 run 都没检出即 BROKEN。否则模板一旦不再给 `°` 挂 `.unit--deg`，这条判据会因为「没有对象」而静默变绿——静默变绿的判据比没有判据更坏。

### 反解与实测

关掉定律量自然态（`DSM_CSS='.optical{vertical-align:baseline !important}'`，与量具写在同一条命令里）→ `fit-rho.cjs` 按角色分参照。`°` 那一对从 `-0.3387 / 0.5817` 变成 **`-0.7000 / 0.7294`**，残差 rms 0.38、最大 0.59 设备px（比多数角色还干净）。**其余六对系数这次重测逐位复现**（最大变动 0.0020，量具格点抖动以内），说明动的确实只有 `°` 一个角色。

19 组合全绿：`°` 从 `[773,777]` 抬到 `[768,772]`，**离 cap 线 0.00 设备px**；全档全态上标偏差最大 **1.00** 设备px（允差 1.5）；其余三条判据读数与改前不可区分（散差 ≤2.50、居中 0.42、主读数 0.44、边距 6±0.52）。趋势斜率不变。肉眼核对 `shots/` 与用户截图同一格：小圈回到右上角，`--°` 缺失态不跳。

允差 1.5 设备px 的依据：这条一次过两个取整面——上标 run 自己的上沿与最大字样的上沿各自被设备网格吸附一回，合起来 ±1 格，再留半格。被守的那个 bug 量级是 4~8 设备px，门再松也抓得住；定在 1.5 只是为了别让「差整整一格」溜过去。

### 两条连带的口径修正

- **形状守卫里「|a|+|ρ| < 1.2」改成「逐项 < 1」**。`°` 的新系数两项天然部分相消（单位的 em/fs 只有 0.74~0.80），和值 1.43 却每一项都 < 1，净抬量 1.2→4.2 CSS px 随字号走。要挡的是「这一项像不像像素」（1 设备px 在本机是 1.75 CSS px，被当成 px 写进来的数必然越过这条线），不是「两项加起来大不大」。
- **跨字体栈这条轴上 `°` 不再是异类**。旧口径下它换栈漂 2~5 设备px（相对中心线），新口径下实测 1~4 设备px（相对 cap 线，5 族栈），与中文标签、箭头同量级——因为 cap 线是同一族字体里量出来的局部参照，比卡片中心线更跟着字体走。换栈仍须整表重测，这条没变。

### 被否证的写法

- **给 `.unit--deg` 补一个 `translateY` 或字面抬量**：这是把①退化成的老路，`tests/opticalCenter.test.ts` 直接红（渲染层不许出现 translateY，也不许有第二处带长度的 `vertical-align`）。
- **把 `°` 留在共线组里、顺手放宽 `TOL`**：散差上限要从 2.5 抬到 7 才容得下它，等于用一条全局判据的失明换一个角色的位置——别的角色从此再也报不了。
- **让 `°` 跟着本读数的数字上沿走**：缺失态 `--` 一进来就上下跳，且全条 bar 的两个温度记号不再齐。
- **改用 CSS `vertical-align: text-top` 之类的原生档**：它对齐的是父元素**内容盒**顶（排版量），不是墨迹上沿；本项目已经用真像素否证过 `fontBoundingBox` 那一类推法（`k=0.479、R²=0.584、残差 1.93 CSS px`），没有理由相信它的兄弟档更靠谱。

## 后续修正六：横向节奏收紧，数字槽 3ch → 2.5ch

用户反馈「水平布局过于分散」，并点名三处：`CPU↔45%`、`GPU↔23% 41% 61°`、`网络↔速度`。根因不是分隔线，而是 `.num` 为 3 位数（100）预留的 `min-width: 3ch` + `text-align: right`：两位数在槽里自带约 1ch 的不可见留白，标签的 `margin-right` 只是叠在它前面。净效果是每个标签到首读数都隔着约 2ch。

第一轮把槽收到 2ch、标签/读数间距收到 2px，实测卡片 490.65 → 410.74 CSS px；用户随后判定「太紧凑」，要求松一点、但必须低于上一版（3ch + 3px 间距那一版）。最终取两版的中间值：

- **`.num` 默认槽宽 `3ch → 2.5ch`**：0–99 的 1↔2 位变化仍不推布局；100 只撑宽 0.5ch 一次（比 2ch 版的宽度呼吸减半），窗口宽度只增不减兜底。
- **标签 `margin-right: 4px → 3px`**；**读数之间 `margin-left: 4px → 3px`**（与上一版相同，靠槽宽差把间距压到上一版之下）。
- **网速段槽位仍是 4ch**（要容纳箭头 + `99.9`）：标签 margin 3px → 2px、上下行间距 3px → 2px，均低于上一版。
- **分隔线横向占位 `13px → 8px`**（线两侧各约 4px）；**卡片左右 padding `9px → 8px`**。

fs=12 的卡片自然宽度 490.65 → 438.68 CSS px（约 −10.6%），介于上一版 459.65 与 2ch 版 410.74 之间；字号 10–18 全档都落在两版之间。垂直红项与改动前逐条一致；完整扫描另在 fs=10 多出两条 `GPU 3/unit "°"` 未检出墨迹（单跑该组合可检出、截图肉眼可见，是 1000px 测量窗下的相位噪声，不是界面变化）。本机 125% 缩放下那批垂直红项是既有问题，不在本轮范围。下次改数字格式（例如网速加小数位）、改字号阶梯或换字体栈时，槽宽与卡宽必须重新跑 `npm run build && npm run measure:alignment`。

## 后续修正七：撤掉定宽槽，横向节奏改成随 `--fs` 的四级

一次 UI 布局审查（frontend-design）量出来的：定宽槽把余量留在**标签与数字之间**，所以读数越长，可见间距越小。fs12 实测——

| 状态 | CPU 标签→数字 | 网络 标签→箭头 | 卡片宽 |
| --- | --- | --- | --- |
| 两位数（45 / 1.2） | 10.00 | 13.31 | 438.68 |
| 三位数（100 / 88.8） | **3.00** | **2.00** | 450.61 |

也就是最需要看清的那一档（CPU/GPU 打满 100%）把间距吃成了「CPU100%」。根因不是 margin：`.num` 的 `min-width: 2.5ch` + `text-align: right` 把放不下的半格全推到左边，正好压在标签的 `margin-right` 上。

**决定：撤掉定宽槽，宽度由内容给；那段空气由标签的 `margin-right` 独占，并让三档间距都随 `--fs` 缩放。**

- `.num` 去掉 `min-width` 与 `text-align: right`，`Reading` 的 `width` prop 与 `NET_SLOT_WIDTH` 一并删除（网络段不再有特例）。
- 节奏取四级，全部无量纲：数字↔单位 `1px`、伴随读数 ↔ 主读数 `0.50×--fs`、标签 ↔ 首读数 `0.58×--fs`、跨段分隔线 `0.83×--fs`（≈fs12 的 1 / 6 / 7 / 10）。**固定 px 会让 fs18 相对变紧、fs10 相对变松**，而字号是唯一的用户量。
- 卡片圆角 `10px → calc(--fs × 0.8)`：卡高本来就随字号呼吸，圆角不跟会让 fs10 近胶囊、fs18 变方角。

实测（fs12，本机 125%）：两位数 **6.95 / 1 / 6 / 9.95**，三位数**逐条同值**——间距不再随位数压缩，改由卡片宽度吸收：fs12 值 438.7 → 447.9（仍低于被否掉的 3ch 版 459.65），fs18 值 563.9 → 606.6（比例不变）。

**代价（认下来的）**：① 位数变化时内容会横向呼吸（100↔99），窗口宽度只增不减只能兜住窗口那一层，卡片内部会动；换来的是标签与数值恒定成对。② 缺失态的 `--` 不再被垫到两位数宽（fs12 missing 438.7 → 421.1）——首帧按缺失态定宽、有数据后由「宽度只增不减」接管，不抖。

垂直判据复验：19 组合与改前**逐条一致**（唯一变化是 fs17 散差 0.5 → 1.0 设备px，仍是格点抖动），说明这轮只动了水平方向。

**连带：亮色标签的对比度。** 同一次审查算出 `--bar-label: rgba(29,29,31,0.48)` 对卡片只有 **3.06:1**——哪怕卡片完全不透明也不到 AA 的 4.5。提到 **0.62** 后 4.67:1（半透明压白壁纸时 4.69:1）。暗色那侧的 0.50 本来就有 4.82:1，不动。这条现在由 `tests/contrast.test.ts` 守着（直接解析 tokens.css 算 WCAG 比值，暗/亮两套都要过）。

**连带：量具的允差按 DPR 归一。** 居中这条判据按 CSS px 报（跨 DPI 可比），但它的**地板由设备网格决定**：基线吸附给 ±0.5 设备px，卡片自己的上下沿又各自吸附一回。旧口径把它写死成 `0.5 CSS px`——撰写时那台机器是 175%，0.5 CSS px = 0.875 设备px，正好压在地板上；换到 125%（1 设备px = 0.8 CSS px）就成了 0.625 设备px，比地板还紧，于是 **fs15 的 ±0.75 CSS px（= 0.94 设备px，判据自己的模型里就写着「最大 1.00 设备px」）会平白报红**。现在地板取 `CENTER_TOL_DEV = 1` 设备px、按每组合实测的 `sf` 折算，`DSM_CENTER_TOL` 退化成「更松的 CSS 下限」（默认 0），横幅与 BROKEN 明细都同时打印 CSS 与设备两种单位。

本机 125% 复跑：`超标 9 → 8、BROKEN 16 → 13`，翻绿的全是格点级的居中项；**边距那批仍然红**（fs10 5.59/7.29、fs11 0.84、fs12 5.49/7.19、fs13 0.74、fs18 0.79），因为它们超出 1 设备px 地板——也就是说它们是这台机器上真实存在的偏差（最大 1.29 CSS px），不是相位噪声，仍按既有口径留着。这条改的是**量具的分辨力**，不是判据本身：地板以上的偏差一条都没放过。
